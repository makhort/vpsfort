vpsfort

vpsfort-tg-bot

A Telegram bot that brings vpsfort's admin messages to the admin's Telegram chat: the alerts, the daily digest (both servers'; the VPN server's arrive through the cluster) and the weekly abuse report. It does for Telegram what vpsfort-xmpp-bot does for XMPP on vpsfort's side, through the same kind of outbox, and nothing else:

  • No link to ejabberd. No ejabberdctl, no database, no XMPP login. It runs as its own user vpsfort-tg-bot, which isn't in the ejabberd group and can't read ejabberd's files.
  • No XMPP account data, and no server addresses, on Telegram. Telegram's servers can read everything a bot sends (bots get no end-to-end encryption). So in alerts and digests account names become pseudonyms and the servers appear only by their node ids (below), and the abuse report goes only as a file encrypted to the admin's OpenPGP key. vpsfort-xmpp-bot's user commands (/invite, /devices, /export, ...) and admin commands (/list, /sessions, ...) are not here.
  • No orders for the servers. Its commands only show its own state; the servers are managed over SSH.

Both bots can run side by side. vpsfort feeds vpsfort-tg-bot only when [notify] tg_outbox is set. Without it, nothing changes.

Where it runs. On a small VPS of its own that joins the vpsfort cluster (the Telegram relay node, vpsfort's deploy/vpsfort-tg.toml), so the XMPP server never connects to Telegram: the XMPP and VPN nodes relay their admin messages to it over the encrypted cluster link, and may limit what it hands them to notices (it can't ban or allowlist anything there). vpsfort's README, "A Telegram relay node", has the cluster side. It can also run on the XMPP server itself: then that server talks to Telegram.

What it sends

From vpsfortIn Telegram

alerts older than ALERT_MAX_HOURS (24) when the bot gets to themdropped, and one message says how many

Commands, from the admin only: /status (uptime, what was sent, what waits in the outbox, the last error), /privacy (what goes through Telegram and what the bot keeps), /help. The bot sets them as its command menu in the admin's chat only. Messages from anyone else get no answer, and a group or channel someone adds the bot to, it leaves. The log only counts them, with the latest sender's numeric id, at most every 10 minutes.

Account names become pseudonyms

vpsfort's admin alerts name XMPP accounts (account alice@example.org registered from …, ejabberd:alice@… under distributed attack, ejabberd log lines as evidence). vpsfort-tg-bot replaces each with [acct:1a2b3c]: the first 24 bits of an HMAC-SHA-256 of the bare address (lower case, resource dropped) under pseudonym.key, a random key made on the first start. It never leaves the server.

  • The same account always gets the same pseudonym, so repeated attacks on one account still show.
  • Without the key, nobody can tell which account it is, Telegram included. A plain hash would not do: account names are few and easy to guess.
  • On the server, vpsfort-tg-bot pseudonym alice@example.org prints an account's pseudonym (as root or vpsfort-tg-bot, with the same PSEUDONYM_KEY).
  • Every address-like local@domain in an alert is replaced (with its /resource), and so is ejabberd:<name> (a bare user name counts as on the first of XMPP_DOMAINS). Alerts never need an e-mail address.
  • A name is everything back to a blank or a character XMPP forbids in account names ("&'/:<>@). Account names may contain ( ) [ ] { } , ; = |, so bob(1)@example.org and a,b@… are hidden whole; brackets in front stay outside ((alice@…) and alice@… get the same pseudonym). Matching too much only hides more.
  • Files are not touched: they go out encrypted as a whole (below).

The servers appear by their node ids

SERVER_NAMES lists each server's own addresses and host names under its node id (vpsfort's [cluster] node_id): node1=192.0.2.10,example.org; vpn=198.51.100.20; tg=203.0.113.10. In alerts and digests, after the account names:

  • an address becomes the node id: cluster peer 198.51.100.20:7946 failing → cluster peer vpn:7946 failing. IPv4 matches as any run of digits and dots, wherever it is (dead:…, ::ffff:…:7946); IPv6 as a run of hex digits and colons that is the address (brackets and IPv4-mapped too), or, when the run is no valid address, starts with it before a colon (…: refused, a port). A run that is another valid address stays: attackers' addresses, also 2001:db8::7:5 next to a server's 2001:db8::7;
  • a host name becomes the node id, subdomains keeping their first labels: example.org:5223 → node1:5223, nextcloud.example.org:443 → nextcloud.node1:443. notexample.org and example.org.example.net are left alone.

List every public IPv4 and IPv6 address of each server. Loopback and unspecified addresses (127.0.0.1, ::, 0.0.0.0) are refused: they are no server's address and appear in many lines. A node id needs a letter other than a to f (node1, vpn, tg, relay): one of hex digits only would join the colons and digits around it into a new address. Without SERVER_NAMES the bot warns at startup and sends the names as they are. The subjects say which server already ([xmpp]).

What does go to Telegram: attackers' addresses, ports, countries and networks; ban decisions; the servers' state (exposure, certificates, cluster) under their node ids; sanitized log lines with account names and server names replaced. A "suspicious login" alert also carries the login's address. That is the point of the alert, but if it was the account owner, it is their address.

Files go out encrypted, as a whole

The weekly abuse report (or any file vpsfort puts in the outbox) is sent only as one OpenPGP message encrypted to the admin's public key (OPENPGP_KEY), never in clear, not even in part: the caption is a fixed line saying how to open it, the name is report-<date>.<ext>.pgp. Telegram sees a file of some size, and that it is OpenPGP.

  • Apps. Android: OpenKeychain (F-Droid, Google Play; in maintenance mode, still working). iPhone: iPGMail (paid, updated in 2026). In Telegram, open the file's menu → Share (or Save to Files) → the app; it asks for the key's passphrase and shows or saves report-<date>.txt.
  • The key. Create it in that app (on the phone, so the secret key never leaves it), or use one you have. A v4 key with an RSA (3072 or 4096 bits) or Curve25519 encryption subkey works everywhere; RSA is the safe choice if you switch between Android and iPhone apps. Export the public key as a file (both apps can share or export it from the key's page), copy it to the server and install it as root: install -o root -g vpsfort-tg-bot -m 640 admin.asc /opt/vpsfort-tg-bot/admin.asc, then restart the bot. Its log (and /status) shows the fingerprint: compare it with the one the app shows.
  • The format. What these apps and GnuPG read: a v3 PKESK packet for each encryption subkey, a SEIPD v1 packet (with MDC) under AES-256, no compression, no file name inside (RFC 9580 advises none). Not SEIPD v2 / AEAD or v6 keys: OpenKeychain can't read them. The bot uses rPGP (pure Rust, MIT/Apache). tests/gpg_interop.rs checks every file decrypts with GnuPG, for RSA-4096 and Curve25519 keys made by gpg.
  • Checks at startup. The key must parse, its self-signatures verify, and it must be a v4 key, not revoked or expired, with an encryption subkey of those kinds that was never revoked. Signatures by other keys (gpg --sign-key, web of trust) are ignored, not taken for broken self-signatures (until 2026-10-17 they stopped the bot). Otherwise the bot stops (exit 78) instead of running without a key. Without OPENPGP_KEY it runs, and files wait, unsent, until they expire after OUTBOX_MAX_DAYS.
  • And at every file. A key (or subkey) that expires while the bot runs is no longer used: files wait, /status says why, and the chat gets a note at most once a day.
  • A file Telegram refuses for good (400 Bad Request, 413 too large) is dropped with a note in the chat.
  • Only the public key is on the server: whoever gets into it can't read reports sent before. The report itself still names the servers' addresses, for the abuse desks; that stays inside the encryption.

Deleting a key gives every account a new pseudonym; old messages then no longer match.

How vpsfort and the bot meet

They share one directory, /opt/vpsfort-tg-bot/outbox (root:vpsfort-tg-bot 1770, sticky), and vpsfort-xmpp-bot's file format (see src/outbox.rs and vpsfort's src/botbox.rs):

  1. vpsfort's notifier writes a copy of each message to the first of [notify] admins (on the relay node, [notify] xmpp = false, or with admins empty: every admin message, its own and the relayed ones, and then only here) as alert-<time>-<n>-<signature>.msg (To: and Subject: lines, a blank line, the text; the signature is for vpsfort's own check, not the bot's). It writes under a dot name first, gives the file to tg_user, and renames it into place. This copy is in addition to the XMPP way, which is unchanged.
  2. The bot looks every 5 seconds. It claims a message by renaming it to .<name>.sending, sends it and deletes it. If sending fails, it renames the file back and tries again (after Telegram's retry_after, or after 30 s). A message left in .sending by a stop is put back at the next start. Messages over 1 MB (vpsfort's are a few KB) are deleted unread. At startup the bot checks it can write the outbox (an OUTBOX_DIR outside the unit's ReadWritePaths can't be), and says so in its log if not.
  3. Unlike the XMPP bot's outbox, vpsfort takes nothing back: there is no plain-text fallback for a copy. When copies wait longer than bot_stuck_after (1h), also ones a bot that died left half-sent (.sending), vpsfort warns the admins the XMPP way, at most once per hour (with no XMPP admins: as a system alert in its journal, relayed to peers with relay_notices).
  4. vpsfort-abuse-report.sh (merge role: on the XMPP server, or any server with vpsfort-tg-bot) puts the weekly report into every outbox it knows: vpsfort-xmpp-bot's, and vpsfort-tg-bot's when vpsfort's [notify] tg_outbox (or ABUSE_REPORT_TG_OUTBOX) is set. On the relay node (role relay) it waits for the report the XMPP server merged and forwarded (ABUSE_REPORT_FORWARD_TO there) and puts that in vpsfort-tg-bot's outbox; if none comes, it merges itself. The bot looks every minute, sends the report encrypted and deletes it. A report not sent within OUTBOX_MAX_DAYS (7) is deleted unsent.

Check it as root: vpsfort -c /etc/vpsfort/vpsfort.toml notify-test --telegram puts a test in the outbox and waits until vpsfort-tg-bot has sent it.

Install from a release bundle

Instead of deploy.sh (step 2 below), without a Rust toolchain: every version tag vpsfort-tg-bot-v<version> gets its bundle, vpsfort-tg-bot-<version>-<commit>-<arch>.zip for each architecture (x86_64-linux-musl, aarch64-linux-musl for arm64, armv7-linux-musleabihf for 32-bit ARMv7 with hardware floating point), as an asset of the tag's GitHub Release (see "Releases" in the repository README); CI also keeps one for every commit as a workflow artifact (they expire and need a GitHub login), and scripts/bundle.sh builds it locally. It holds the static binary, the unit, config.env.example, SHA256SUMS and install.sh.

Download and verify (on your machine, then copy the zip over, or on the server): take the zip for the server's architecture (uname -m: x86_64, aarch64, or armv7l for armv7) from the GitHub Release of the version's tag, with the GitHub CLI or from the Releases page (each crate's releases are tagged vpsfort-tg-bot-v<version>):

arch=x86_64-linux-musl     # the server's: aarch64-linux-musl (arm64), armv7-linux-musleabihf (32-bit ARM)
gh release download vpsfort-tg-bot-v0.5.3 --repo makhort/vpsfort --pattern "*-$arch.zip*"   # the zip, its .sha256 and .sigstore.json
sha256sum -c vpsfort-tg-bot-*-$arch.zip.sha256              # the download is intact (macOS: shasum -a 256 -c)
gh attestation verify vpsfort-tg-bot-*-$arch.zip --repo makhort/vpsfort --source-ref refs/tags/vpsfort-tg-bot-v0.5.3

gh attestation verify (after gh auth login) checks the signed build provenance: that this repository's CI built exactly this zip from that tag. With --bundle vpsfort-tg-bot-*-$arch.zip.sigstore.json it checks the attestation attached to the Release instead of fetching it from GitHub. Only a public repository's releases have one (GitHub offers attestations for private repositories only with Enterprise Cloud).

On the server (apt install unzip or dnf install unzip if needed):

arch=x86_64-linux-musl     # as above: aarch64-linux-musl, armv7-linux-musleabihf on ARM
unzip vpsfort-tg-bot-*-$arch.zip && cd vpsfort-tg-bot-*-$arch
sudo ./install.sh          # install or upgrade; the first time also /opt/vpsfort-tg-bot/config.env
sudo ./install.sh rollback # back to the previous version

The first install, as with deploy.sh, doesn't start the bot while the token and admin id are placeholders: continue with step 3. install.sh checks every file against SHA256SUMS in a copy only root can write, then runs the same installer as deploy.sh (./install.sh --check only checks the files).

Install from a package

The same release has a package per architecture, for the distribution's package manager instead of install.sh: vpsfort-tg-bot_<version>-1_<arch>.deb (amd64, arm64, armhf; Debian, Ubuntu and their derivatives) vpsfort-tg-bot-<version>-1.<arch>.rpm (x86_64, aarch64, armv7hl; Fedora, RHEL and its rebuilds) and vpsfort-tg-bot-<version>-r0.<arch>.apk (x86_64, aarch64, armv7; Alpine, with OpenRC: below), each with its .sha256 and .sigstore.json, downloaded and verified as the bundle above (--pattern "*.deb*", "*.rpm*" or "*.apk*"). CI keeps them for every commit as workflow artifacts, and scripts/package.sh builds them locally (cargo install cargo-deb cargo-generate-rpm --locked once, and python3 for the .apk, which scripts/apk.py at the repository's root writes; none needs dpkg, rpm or apk-tools, so it runs on macOS too; --target aarch64-unknown-linux-musl or armv7-unknown-linux-musleabihf for the ARM ones). Or from the signed apt and dnf repository on GitHub Pages, once it is set up (the repository README, "Deployment"), where apt upgrade and dnf upgrade then bring new versions.

sudo apt install ./vpsfort-tg-bot_0.5.3-1_amd64.deb     # Fedora, RHEL:  sudo dnf install ./vpsfort-tg-bot-0.5.3-1.x86_64.rpm
sudoedit /opt/vpsfort-tg-bot/config.env                 # the first install put the template there
sudo systemctl enable --now vpsfort-tg-bot

The package puts the same files in the same places as install.sh (/opt/vpsfort-tg-bot with the binary and config.env.example, the user vpsfort-tg-bot, /var/log/vpsfort-tg-bot, the logrotate rule), except the unit, which is in /usr/lib/systemd/system. Its post-install step does what install.sh does apart from copying files: the user, config.env from the template the first time, the owners and modes, the outbox and the log directory; and it prints what is left to do (step 3 of "Setup": the token and ADMIN_CHAT_ID from pair, your OpenPGP key). dpkg-reconfigure vpsfort-tg-bot (rpm: dnf reinstall ./vpsfort-tg-bot-*.rpm) runs that step again, e.g. after copying a key there. apt remove vpsfort-tg-bot (dnf remove) stops the bot and keeps /opt/vpsfort-tg-bot; apt purge vpsfort-tg-bot removes it with the state and keys (rpm: by hand).

Nothing starts on its own. The first install puts the template in place and prints what to fill in; you enable the service once it is filled in. An upgrade keeps the config and restarts the service only if it was running and the config is filled in. Over a bundle or deploy.sh install the package takes over: the config, state and keys stay; the bundle's unit in /etc/systemd/system (it would shadow the package's) and its rollback files go, and the service is enabled again on the package's unit if it was (vpsfort's integrity watch reports the removed unit as a warning once). Replacing the config: when a terminal is there, the install asks whether to replace the config with the new template (the old one kept with the suffix .old); Enter, a timeout of a minute, no terminal or DEBIAN_FRONTEND=noninteractive keep it. VPSFORT_PACKAGE_CONFIG=replace (or keep) answers without asking: sudo VPSFORT_PACKAGE_CONFIG=replace apt install ./<file>.deb. Rollback is installing the previous version's package (apt install ./<old>.deb --allow-downgrades, dnf downgrade ./<old>.rpm): there is no .prev file.

Alpine (apk, OpenRC): apk add --allow-untrusted ./vpsfort-tg-bot-<version>-r0.x86_64.apk puts the same files in the same places, with the OpenRC script /etc/init.d/vpsfort-tg-bot instead of the unit: the settings exported from config.env as EnvironmentFile= does, supervised by supervise-daemon and started again 5 seconds after a crash; systemd's sandboxing has no equivalent there. The package is unsigned, hence --allow-untrusted: sha256sum -c and the attestation verify it. Its install scripts are POSIX sh and do what the post-install step above does: the user, config.env from the template the first time, the owners and modes, the log directory; an upgrade restarts a running bot. Then rc-update add vpsfort-tg-bot default && rc-service vpsfort-tg-bot start. apk del vpsfort-tg-bot stops it and keeps /opt/vpsfort-tg-bot. Not yet run on an Alpine host: CI installs the package in an Alpine container.

Setup

  1. Create the bot with @BotFather: /newbot, then /setjoingroups → Disable (it serves one private chat). Keep the token secret.
  2. Deploy from the Mac (builds a static Linux binary, runs scripts/ci.sh first), to the relay node: first vpsfort (../vpsfort/deploy/deploy.sh tg deploy/vpsfort-tg.toml, after setting the peers and peer_accept on the other nodes), then the bot: 
    ./deploy/deploy.sh          # copies to tg:/tmp/vpsfort-tg-bot-deploy, prints the root command (the XMPP server's ssh alias as argument for that server)
    The first install creates the vpsfort-tg-bot user, /opt/vpsfort-tg-bot and config.env (from deploy/config.env.example, every option with a reasonable value). It doesn't start the bot while the token and admin id are placeholders.
  3. Fill in config.env as root: put the token in TELEGRAM_TOKEN. Then find your user id: 
    set -a; . /opt/vpsfort-tg-bot/config.env; set +a; /opt/vpsfort-tg-bot/vpsfort-tg-bot pair
    It prints a link and a code. Open the link (or send /start <code> to the bot) from your Telegram account, and it prints ADMIN_CHAT_ID=…. Put that in config.env, check SERVER_NAMES, install your OpenPGP public key as OPENPGP_KEY (above), then systemctl enable --now vpsfort-tg-bot (or run install.sh again). pair reads the bot's updates itself, so the service must be stopped meanwhile.
  4. Tell vpsfort (optional, off by default; vpsfort-tg.toml has it already). In [notify] of /etc/vpsfort/vpsfort.toml (a vpsfort with tg_outbox support must be deployed first: older ones reject the key): 
    tg_outbox = "/opt/vpsfort-tg-bot/outbox"
tg_user = "vpsfort-tg-bot"
    The weekly abuse report job reads tg_outbox from there too. On a server with ejabberd, leaving admins empty sends admin messages to Telegram only (users are still warned over XMPP). For a relay node, in /etc/default/vpsfort-abuse-report: ABUSE_REPORT_SEND_TO=<the XMPP server>:7946 there, and on the XMPP server ABUSE_REPORT_PEERS="vpn tg" and ABUSE_REPORT_FORWARD_TO=<tg>:7946. Then systemctl restart vpsfort and run the notify-test --telegram check above. Adding vpsfort-tg-bot.service to vpsfort's [sources] services gets an alert when the bot fails.

install.sh rollback goes back to the previous binary and unit (kept while the running version runs cleanly).

Renamed from tgbot (2026-10-17). The bot was tgbot, installed as /opt/tgbot/tgbot, run by tgbot.service as the user tgbot, logging to /var/log/tgbot. The first install.sh of the new name moves an old install over on its own, before installing:

  • stops and disables tgbot.service, removes it and /etc/logrotate.d/tgbot (local changes in tgbot.service.d/ move to vpsfort-tg-bot.service.d/);
  • renames the user and group tgbot to vpsfort-tg-bot (same ids, so every file stays theirs);
  • moves /opt/tgbot to /opt/vpsfort-tg-bot and /var/log/tgbot to /var/log/vpsfort-tg-bot: the state (Telegram's queue position, messages to delete), the pseudonym key (so every account keeps its pseudonym), OPENPGP_KEY, the outbox and the log carry over;
  • rewrites the old paths in config.env (the previous file stays as config.env.pre-rename) and adds BOT_STATE_PATH and LOG_DIR if they were missing;
  • keeps the old binary as vpsfort-tg-bot.prev if it ran cleanly, so rollback works right after the move (with the new unit and paths; the old unit is not kept);
  • in /etc/vpsfort/vpsfort.toml and /etc/default/vpsfort-abuse-report, replaces /opt/tgbot, tg_user = "tgbot", "tgbot.service" and ABUSE_REPORT_TG_OWNER=tgbot (each changed file stays as <file>.pre-rename-<time>), checks that vpsfort accepts the config (else puts it back and says what to change by hand) and restarts vpsfort.

Deploy the current vpsfort first (its abuse report unit may write only to the new outbox paths, and its tg_user default is now vpsfort-tg-bot); install.sh warns while the installed abuse report unit names only the old ones. Running it again changes nothing more; if both /opt/tgbot and /opt/vpsfort-tg-bot exist, it stops and asks you to keep one. The bot's token and chat stay the same; Telegram doesn't see the rename.

Telegram sees the address of the host vpsfort-tg-bot runs on; in the messages the servers appear by their node ids only, as far as SERVER_NAMES lists them. The host needs outgoing HTTPS to api.telegram.org. TELEGRAM_API_URL can point to a local Bot API server instead (plain HTTP only on localhost).

Retention and what the bot keeps

  • On Telegram: messages stay in the chat until deleted. With DELETE_AFTER_HOURS, the bot deletes its own and your messages in the chat after that long. Telegram allows bots this only within 48 hours, so messages from a longer downtime have to be deleted in the app. /privacy says which applies.
  • On the server: bot.log (14 days: weekly rotation, one old copy), state.json (the next update id and, with auto-delete, message ids and times: no text), pseudonym.key, and outbox files until they are sent (or expire). Nothing the bot sends is written anywhere else on the server.

The unit drops every capability, makes the whole file system read-only except /opt/vpsfort-tg-bot and /var/log/vpsfort-tg-bot, allows only IPv4 and IPv6 sockets, denies writable-executable memory, and is held to 128 MB of memory (MemoryMax).

Why not a Telegram crate

The suggested telegram-rs-2 (0.1.2) served as a reference for the API's shape but is not a dependency:

  • it has no sendDocument, and its Message lacks from and date;
  • its reqwest uses the default TLS (OpenSSL), which breaks the static musl build;
  • its errors carry reqwest's URL, which holds the token, into logs;
  • it pulls in a proc-macro crate from the same single author (runs at build time), with a few dozen downloads in all.

src/api.rs calls the half dozen methods it needs directly, over reqwest with rustls and ring (like vpsfort-xmpp-bot's TLS). It checks the token's shape before it goes into a URL and strips URLs from errors. Formatting goes as entities, never Markdown or HTML, so nothing in a log line can change how a message displays.

Build and test

./scripts/ci.sh            # fmt, clippy, tests, cargo audit, static Linux binary

The static build needs rustup target add x86_64-unknown-linux-musl (for ARM: aarch64-unknown-linux-musl, armv7-unknown-linux-musleabihf, built with TARGET=... ./deploy/deploy.sh) and rustup component add llvm-tools (see .cargo/config.toml, the same as vpsfort-xmpp-bot's). tests/fake_telegram.rs runs the delivery code against a fake Bot API server on 127.0.0.1: an alert with account names and server addresses replaced, the report held back without a key and then sent encrypted (nothing of it in the request, the admin's key opens it), flood control (429 retry_after), strangers ignored, the state across a restart, auto-delete and its 48-hour limit. tests/gpg_interop.rs decrypts the files with GnuPG when gpg is installed (brew install gnupg), in a throwaway GNUPGHOME, and checks keys that expire. Not yet tried against the real Telegram or on a phone.

Fuzzing. What comes from outside (vpsfort's outbox files with attackers' log text in them, Telegram's replies, the key file, SERVER_NAMES) goes through four cargo-fuzz targets (code in src/fuzzing.rs):

  • alert_text: an outbox file through the whole way to Telegram. Besides no panics, it checks the promises with rules of its own: no name@domain and no ejabberd:<name> left, no configured server address or host name left, nothing left to replace on a second pass, and every message as Telegram takes it unchanged (1 to 4096 UTF-16 units, no blanks at the ends, no control characters, entities inside the text and not splitting a UTF-16 pair).
  • telegram_reply: Bot API replies (updates, errors, sent messages) and state.json; no update with an id may be lost.
  • openpgp_key: the key file; whatever is taken as a key must encrypt, with nothing in clear.
  • server_names: a SERVER_NAMES value and a text (split at the first NUL byte).

tests/fuzz_smoke.rs runs them on stable on realistic inputs, the seeds in fuzz/seeds/ and a few thousand mutations, so cargo test keeps them working; a failing input is saved as target/fuzz-smoke-<target>.bin (VPSFORT_TG_BOT_WRITE_SEEDS=1 cargo test --test fuzz_smoke regenerates the seeds; the keys in them are new and throwaway). The real search needs nightly:

rustup toolchain install nightly --profile minimal && cargo install cargo-fuzz --locked   # once
cargo +nightly fuzz run alert_text fuzz/corpus/alert_text fuzz/seeds/alert_text -- -dict=fuzz/alert_text.dict -max_total_time=600

New inputs collect in fuzz/corpus/, crashes in fuzz/artifacts/ (both git-ignored). The regression-* seeds are inputs the first runs (2026-10-17) failed on, all fixed: a server address inside a longer run (dead:…, …:ad:192.0.2.10, 2001:db8::10.example…), an address with junk after a colon, two addresses touching (a@x{@y), an ejabberd:[acct: that wasn't a pseudonym hiding the name after it, brackets alone taken for an ejabberd: name, a hex-only node id rebuilding an address, an address glued to another (198.51.100.20db8::, now replaced until nothing changes), a long subject cut on a blank. The smoke test found the first of these within a second. Later the same day, vpsfort-mail-bot's fuzzing of the same code found a server address that, replaced by its node id, completed an address (admin@::ffff:192.0.2.10 → admin@node1): the account pass now runs again after the server pass (regression-server-makes-address).
