1. vpsfort in one minute

vpsfort is one static Rust binary for a self-hosted Linux server. It does what usually takes four or five separate tools:

  • It bans attackers in the kernel firewall seconds after they show themselves.
  • It watches the host for the ways intruders stay in.
  • It notices when its own view goes dark: a log source that stops, a firewall that was flushed, a scan that was killed.
  • It tells the admins over end-to-end-encrypted channels (or sanitized, to a push service), and warns the users whose accounts are under attack.
  • It shows the whole cluster on one read-only HTTPS page, and to Prometheus (vpsfort-web, optional).

Several servers share what they see over an encrypted peer-to-peer link. There is no central server and no vendor in between: the web console only asks the nodes, with a key of its own that can't make a ban.

Key numbers (measured, from the README):

  • ~11 MB static binary with no runtime dependencies (the optional web console is another ~4 MB).
  • ~10 MB RAM for a real month of traffic (~50 MB with the offline geo database). The hard limit is 128 MB, and it held in a synthetic flood of 450,000 sources.
  • A real month of logs (~210,000 records) replays through the full engine in about one second: 185 bans of 93 targets. No address that ever logged in was banned.
  • Tripwire ports banned about 7,500 scanners on first contact in that month.

2. Who it is for, and who it is not for

A good fit:

  • One to about ten Linux servers you run yourself: Debian or Ubuntu, or Fedora and RHEL with dnf and firewalld; x86_64 (the ARM builds are untried on servers, see below); systemd.
  • SSH, XMPP (ejabberd), Nextcloud and WireGuard hosts, and the common web, database and mail servers through built-in patterns (Apache, nginx, HAProxy, Prosody, MySQL/MariaDB, PostgreSQL, MongoDB, Redis/Valkey, Postfix, Dovecot, ownCloud). Other services count through regex patterns of your own.
  • Admins who want alerts on their phone, encrypted, with nothing about their users or attackers sent to a vendor.
  • Small machines: it is built to stay within a 128 MB memory limit next to the services it protects.
  • Linux desktops and laptops, with a profile of their own (not yet run on one).

Not a good fit today:

  • Fleets of dozens of hosts or more that need fleet management, roles, several users and compliance reports. vpsfort's web console shows dozens of nodes to a few equal admins, read only by design, without fleet management or roles. Look at Wazuh, the CrowdSec Console or a commercial EDR.
  • Web-application-heavy hosts that need a WAF, captchas or CDN integration. vpsfort can enforce a WAF's decisions at the firewall ([waf], with CrowdSec's formats built in), but it inspects no HTTP request itself and answers none: run CrowdSec AppSec, ModSecurity or Coraza for the detection, and a CDN or an HTTP bouncer for captchas.
  • Other platforms: Windows, macOS, BSD. Alpine (OpenRC, a syslog file as the input) is packaged and installed in CI but hasn't run on an Alpine host; ARM bundles (arm64 and 32-bit ARMv7) are built and tested in CI but haven't run on an ARM server yet. Fedora runs in production; RHEL and its rebuilds are untried (CI installs the .rpm on AlmaLinux 9).
  • Organisations that need a vendor: a support SLA, certified compliance evidence, or a 24/7 security operations team.

ScoringTwo decaying scores (10 min and 12 h half-life) add up every signal from every service. A scanner that touches SSH, XMPP and closed ports a little each still reaches a ban. Weights are calibrated on a real month of logs.One model for everything: tuning means weights and thresholds, not per-service rules. Subnet bansStarts at /24 (IPv6 /64) and grows towards /16 (/48) only as nearby bans appear, at most 2 bits a step. It never covers a protected address. A login from inside a subnet keeps it from a subnet ban only until it shows twice what a ban needs, so one registered account can't keep a network of attackers open. With the geo database, it never grows into another provider's network.The provider boundary needs the [geo] ASN database. A stricter policy, such as blocking a whole network or country now, needs feeds. CSF blocks countries out of the box.
Tripwires and honeypotsOne SYN to an unused telnet, RDP or database port bans. Kernel tripwires log these hits from vpsfort's own nftables rules, so UFW's log limit (about 3 lines a minute) doesn't hide scans. Honeypot ports complete the TCP handshake, so their evidence can't be forged, and keep the scanner's first bytes (a Telnet login, an HTTP request, the method an RPC probe calls) for the abuse report; with prompts on, a Telnet bot types its login into the evidence (55 of 71 connections in a day on a honeypot node) and a MySQL client names its account, and a catch-all decoy site on the real web server bans web scanners on their first request. Dedicated honeypot nodes feed all of this to the cluster.A blocked SYN can carry a forged source address. vpsfort limits the damage: such evidence never bans an address that logged in recently, replies always pass, and with honeypots set it is worth half a ban. A spoofer can still get outsiders banned for an hour.
Canary accountsNo accounts to create. On a key-only host, ssh = ["*"] makes every unknown user name a ban. A successful login to a canary is a critical alert.fail2ban, CrowdSec and Wazuh can do this with a filter of your own. vpsfort just has it built in.
Account protectionDistributed guessing against one account from several addresses; a login right after failures (possible compromise); a login from a new network or provider for that account; a login with a never-seen SSH key.Covers XMPP, SSH, Nextcloud, the built-in services and your patterns only. Wazuh covers far more authentication sources (PAM, Windows, cloud services).
False positivesShadow mode lifts its own "bans" when the address later logs in, and says so. An address that logged in recently isn't banned for that service's typos and reconnects. Private, CGNAT, loopback and link-local addresses are never banned.Login trust is a heuristic. An attacker behind the same carrier NAT as a user gets the same excuse for that service's noise; real failures still raise an alert.
Testingreplay runs journal exports through the whole pipeline without touching the firewall, and opens the result in the TUI.CrowdSec's replay mode and cscli explain are as capable, and better documented for writing new scenarios.

5. Firewall enforcement

Bottom line: vpsfort's enforcement takes the most care not to break the server itself (Docker, flushed rulesets, replies, oversized feeds). It covers the Linux firewalls (nftables, firewalld, ipset, ufw, iptables) but no BSD or Windows ones, and CrowdSec reaches the HTTP layer and CDNs.

Where bans sitIts own nftables table at prerouting, right after connection tracking. It runs before ufw's chains and before Docker's DNAT, so your own ALLOW rules can't shadow a ban, and Docker ports are covered without touching DOCKER-USER. It never edits your rules. On Fedora and RHEL it can keep everything in firewalld instead: its own ipsets, a drop zone and a forwarding policy, visible with firewall-cmd. The ipset backend is iptables with one set lookup however many bans.Linux only: no pf, ipfw or Windows. The ufw fallback loses Docker coverage, rate limits and feeds; the firewalld backend has no rate limits or feeds, and its entries end only while vpsfort runs. The firewalld, ipset and nftables backends ran on a Fedora 44 test server; the plain iptables backend has not yet run on a real host.
ExpiryBan timeouts live in the kernel: if vpsfort stops, bans still end on time. After a reboot it re-applies what is still active.CrowdSec's firewall bouncer works the same way.
Self-healingDebian's and Ubuntu's nftables.conf starts with flush ruleset, so a restart of nftables deletes every ban. vpsfort notices within 30 s, rebuilds every set and chain, re-adds the bans with their remaining time, and raises a high alert. The same after firewall-cmd --reload or a firewalld restart, and after its iptables chains are flushed (both seen on the Fedora server). A single change the firewall program refuses, an unban included, is kept and tried again every 30 s, with a high alert while it keeps failing; a firewall program that hangs delays the retries, not the daemon. The ufw backend compares its deny rules with the bans it holds at every start.fail2ban restores its chains too, but only at its next ban action.
Replies to the server's own connectionsBans drop after connection tracking, so replies always pass: DNS, mail relay, update mirrors, federated XMPP servers. A forged packet that gets such an address banned can't cut the server off.The chains dropped a test client on the Fedora server, and on a production server both pings and a TCP connection to addresses banned there got their replies.
Rate limitsPer-source [[ratelimit]] entries in the kernel, from the first packet, Docker ports included. An IPv6 source is its /64, one customer's network, so a host that picks a new address for every connection gets no new allowance. A source's entry ends soon after its last connection (a minute for a rate per second, ten for one per minute, two hours for one per hour), so a flood of forged sources can't fill the table for long. status shows their drop counters.nftables backend only (status says so under the others); an older nft that doesn't take the /64 rule counts per address, and vpsfort says so. CSF has richer flood controls (SYN floods, per-port and per-connection limits).
FeedsDownloads with curl (the binary has no TLS library) and keeps the last good copy. It drops bogons, prefixes wider than /12, and anything overlapping your allowlist or peers. A refresh that suddenly covers far more address space is refused.A few public lists (Spamhaus DROP and ASN-DROP, FireHOL); no curated commercial lists. nftables, ipset and firewalld backends (firewalld: 50,000 networks per list). CrowdSec's blocklists are larger and updated more often.
Countries and networks[geoblock] drops whole countries (or all but some) and networks by AS number, from the DB-IP Lite databases it already holds for labels: no download, no second database, about 1 MB while the list is computed. Protected addresses are cut out exactly. China is about 15,000 networks, everything but one country about 28,000. On the Fedora server two blocked countries timed out and a third connected.The free DB-IP Lite data misplaces some addresses and is refreshed monthly: coarse, not a curated list; a commercial database (DB-IP's IP to Country as it is) can replace it. ufw and plain iptables can't hold it; firewalld takes at most 50,000 networks. CSF's CC_DENY and CC_ALLOW have been doing this for years; vpsfort's [geoblock] ports limits a country block to some ports (SSH and XMPP closed, the web site open) the same way.
HTTP layer[waf] blocks what a WAF decides at the firewall, for every port and, as bans, on every cluster node: CrowdSec's local API, cscli output and blocklist mirror are read as they are, any other app through JSON, CSV, regex or plain-list formats. Its decisions get the protections of an operator ban (allowlists, peers, recent logins), are lifted when the WAF drops them, and large blocklists go into sets of their own.No WAF of its own, and no HTTP-level response: a banned visitor just times out. No captcha, no ban at the CDN or edge. CrowdSec's remediation components and WAF cover that layer. [waf] is tested against CrowdSec's documented formats, not yet run against a real CrowdSec.

ClusterXChaCha20-Poly1305 under a key derived from a fresh X25519 exchange per connection (the shared key authenticates the exchange; a recording stays unreadable if the key leaks later), and only peers may connect. Facts are de-duplicated and forwarded up to 3 hops. Suspicion is shared too, so an address that probes every server a little still adds up to a ban. A shared ban carries up to three of its evidence lines, worded as the abuse reports word them, so a peer's log and the console say what the source did, not only its score. A limited peer (peer_accept) can send messages but never ban anything. Optional node identities: each node signs its own facts and files with an Ed25519 key of its own, pinned on the others, so a broken-into node (or a stolen cluster key) speaks only for itself, and a node is dropped by deleting its key, without a new cluster key. Key rotation is staged in three rounds, without a gap.Without node identities, every unlimited key holder is fully trusted: a broken-into node can ban on the others under any name, for at most max_remote_ban. With them, it can still ban for itself, and still read what the others share until the cluster key is rotated. Keys are pinned by hand in each node's config, with no PKI or enrollment. Node identities run on the authors' five servers, each pinning the other four's keys and requiring signatures; a fact refused for its signature has not been seen yet. It is sized for a handful of nodes, with no fleet management.
Threat intelligenceYour data stays yours: no vendor sees your attackers or your users. Reports from several nodes are merged, and the result reaches the admin encrypted. The web console shows the last day's or week's at any time, merged across the nodes, one entry per network owner, each copied or saved as the e-mail to its abuse desk, or opened in your mail program with the mailbox looked up (RDAP); a network is marked as mailed, and one banned again after that shows "seen again". 15. What vpsfort does not do (yet)

Know these before you adopt it:

  • No HTTP layer of its own: no WAF, captcha or CDN integration. It can enforce a WAF's decisions at the firewall ([waf]: CrowdSec, or any app that gives out a list).
  • A limited set of built-in sources: sshd, ejabberd, the kernel log, Nextcloud, su and sudo, PAM and the audit log, and 24 common services (web servers and proxies, HAProxy, Prosody, Synapse, databases, Redis, mail, ownCloud, Forgejo, Vaultwarden, Keycloak, authentik, OpenVPN, FTP, Jellyfin), the latter tested against log lines but not yet on a host. Everything else needs regex patterns of your own.
  • One platform: Linux. Debian, Ubuntu and Fedora (systemd and journald) run it in production; Alpine (OpenRC, a syslog file) is packaged but untried on a host, and the ARM builds haven't run on an ARM server.
  • No control from a browser, by design: vpsfort-web shows the cluster to a few admins, with a REST API and Prometheus metrics, and changes nothing on the servers: a browser, with its extensions and the exploits aimed at it, is no place to hold the firewall's controls, whatever the login method. What it lacks: roles (every admin sees everything), and age.
  • No crowd-sourced intelligence (only CrowdSec has one). It has static public feeds, country and network blocking from a free database that misplaces some addresses (a commercial one, read as it is, can take its place), and a CrowdSec's decisions through [waf].
  • Host watches poll (every minute, with inotify waking the file watch at once) or run once a week; they don't see which process did what. There is no tamper protection against root.
  • No CVE matching, hardening benchmark or compliance reports (the hardening audit covers sshd and the kernel's sysctls only).
  • Six alert channels: XMPP, Telegram, e-mail, Signal, Matrix, and ntfy, Gotify or a webhook.
  • A young package repository: the signed apt and dnf repository on GitHub Pages is built by CI after each release (it needs a signing key in the repository's secrets); apt and dnf have installed from it, on one server each, and dnf has upgraded from it once. Without it: .deb and .rpm files from the releases, installed one by one, or a release zip with install.sh.
  • Young: version 0.8.0, running on the authors' own servers only, written by one maintainer in collaboration with an AI model (see the README). It has had internal security reviews, but no independent audit.
  • Covered by tests, not yet run on a host: the plain iptables backend, sudo and new-SSH-key alerts, PAM failures and audit alerts, the built-in sources for common services, [waf] against a real CrowdSec, the Telegram relay node and the Telegram, Signal, push and XMPP-client bots against their real services, the desktop profile, the Alpine package, and the ARM builds (Evidence so far). Users' own warnings work in tests but have not yet been confirmed reaching a user.
  • Forged sources: evidence that rests only on blocked packets can name a forged source. vpsfort limits the harm, but someone who forges packets can still get outsiders banned for an hour.

In production. 17. Which tool for which situation

if you ...consider
run 1 to 10 self-hosted Linux VPS (SSH, XMPP, Nextcloud, WireGuard) and want one small tool with encrypted alerts and nothing sent to a vendorvpsfort
want to drop whole countries cheaply, from an offline database, with the rest of vpsfortvpsfort [geoblock]; for per-port country rules, CSF
want a few servers on one read-only web page and in Prometheus, without a SaaS consolevpsfort with vpsfort-web
want to hand a hosting provider the evidence against one of its customers, as a link or a ready e-mailvpsfort-web's address pages and abuse tab
mostly need SSH brute-force protection on any Unix, with minimal setupsshguard or fail2ban
protect many different services and want ready-made filtersfail2ban or CrowdSec
run web applications and want a WAF, crowd intelligence and proxy or CDN integrationCrowdSec with AppSec
need compliance reports, CVE detection and one console for dozens of hosts on several operating systemsWazuh, self-hosted or Cloud
run cPanel or DirectAdmin shared hostinga CSF fork, or Imunify360
need runtime visibility into containers and KubernetesFalco or Tetragon
need a vendor, a 24/7 security operations team, or must meet insurance requirementsa commercial EDR / MDR

18. Good companions

vpsfort works well next to:

  • unattended-upgrades or dnf-automatic, to install what vpsfort's patch status reports.
  • An external uptime and certificate monitor, which sees the host from outside, even when it is down. Cluster peers already report a node that stops answering for 5 minutes.
  • A WAF for web applications: Coraza or ModSecurity, or CrowdSec AppSec with an HTTP-level bouncer only. Keep one ban manager per host: running fail2ban or CrowdSec's firewall bouncer next to vpsfort bans twice and splits the evidence between them.
  • Lynis, for a periodic hardening audit.
  • Falco or Tetragon, where containers matter.
  • ClamAV, whose results vpsfort reads and reports.
  • An off-host log archive (systemd-journal-remote, rsyslog) and backups, for forensics.

19. Trying it

  1. Check the requirements: Linux with systemd (x86_64; ARM builds untried on servers; the Alpine package untried on a host), and one of nftables (recommended), firewalld, ufw, iptables or ipset (Requirements).
  2. Download a release bundle and verify its checksum and build provenance (Install from a release bundle).
  3. Install with a template: vpsfort.toml for an XMPP server, vpsfort-standalone.toml for a host with SSH and UFW only, vpsfort-tg.toml for a Telegram relay node, vpsfort-honeypot.toml for a dedicated honeypot node; each has a -dnf variant for Fedora and RHEL.
  4. Run in shadow mode (the default) for one to two weeks: it decides, but bans nothing. Watch vpsfort tui, and look for "likely false positive" alerts. You can replay a week of your journal first: 
    journalctl -u ssh -k --since -7d -o json > week.json && vpsfort -c /etc/vpsfort/vpsfort.toml replay week.json
  5. Enforce: set mode = "enforce", restart, and check nft list table inet vpsfort (or firewall-cmd --info-zone=vpsfort). To roll back, switch to shadow mode and delete the table (Rollout).
  6. Add more when you want it: cluster peers, the bots, the web console (vpsfort-web), blocklist feeds, country blocking, honeypot ports, built-in sources and patterns for your other services. Before the console goes on a server, vpsfort-sim runs it on your laptop from a few days of your decision logs (the health cards it can't read from a log are made up, and say so).
