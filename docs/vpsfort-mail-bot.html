vpsfort

vpsfort-mail-bot

A send-only mail bot for vpsfort: it mails vpsfort's admin alerts, the daily digest and the weekly abuse report to the admins, each mail OpenPGP-encrypted as a whole, subject included. It goes out through a mail server over SMTP: the local Postfix, or any other server with TLS. It reads no mail and takes no orders; the servers stay managed over SSH.

It is the third copy bot next to vpsfort-xmpp-bot (OMEMO) and vpsfort-tg-bot (Telegram), and works like vpsfort-tg-bot: vpsfort puts a copy of every admin message in its outbox, the bot sends it and deletes it. It can run on any vpsfort node, alone or next to the other bots, or on a relay node of its own (as vpsfort-tg-bot does, deploy/vpsfort-tg.toml in vpsfort).

What a mail looks like

Every mail is PGP/MIME (RFC 3156): multipart/encrypted, one OpenPGP message holding the whole content. Mail servers on the way, and the mailbox provider, see only:

  • the envelope and the outer headers: From, To, Date, Message-ID (random), the size, and the subject ... (OUTER_SUBJECT);
  • Auto-Submitted: auto-generated (no auto-replies), and, if the bot signs, an Autocrypt header with the bot's public key.

Inside, encrypted: the real subject ([vpn] vpsfort: password guessing blocked) and the headers again as "protected headers" (protected-headers="v1"), which Thunderbird, K-9 / Thunderbird for Android, FairEmail and Delta Chat show in place of ..., then the text, quoted-printable (any line length, any character). Text from attackers in alerts (user names they tried, URIs) never reaches a header unencoded and can't start a MIME part.

  • Alerts and the digest: one mail each, the message's text as the mail's text.
  • The weekly abuse report: the report as the mail's text (it is text). A file that isn't UTF-8 text would be attached instead.

The OpenPGP format is the one every client reads: v4 keys (RSA, or Ed25519/Curve25519), a v3 PKESK per recipient key, SEIPD v1 with MDC under AES-256, no compression (not AEAD / v6, which many clients can't read yet). tests/gpg_interop.rs has GnuPG decrypt the mails and check the signature, for RSA and Curve25519 keys.

Keys

  • OPENPGP_KEY (required): the recipients' public keys, in one file (armored or binary, one or more keys). Each address in MAIL_TO gets the key whose user id names it; with a single key, that key serves every address (logged as a warning when the user id differs). An address without a key stops the bot at the start (exit 78): nothing goes out in clear. A key that has expired, at the start or later: that recipient gets nothing (logged every 10 minutes) until the key is replaced; with no usable key at all the bot doesn't start, and when the last one expires while it runs, messages wait and vpsfort warns about them after bot_stuck_after. Only the key's own signatures count: certifications by others (gpg --sign-key, web of trust) are ignored, not taken for broken self-signatures.
  • SIGNING_KEY (optional): the bot's own key, made once with vpsfort-mail-bot keygen (Ed25519, no passphrase: it would sit next to the key anyway). Every mail is then signed, and the public key goes out in the Autocrypt header (autocrypt.org Level 1), so clients that read it (Thunderbird, K-9/FairEmail, Delta Chat) learn it from the first mail and show the signature as valid. Others: import signing.key.pub.asc. The key proves a mail comes from the bot; it can't read anything.

Only public keys of the recipients are on the server: whoever gets into it can't read mails already sent.

Sanitizing (optional)

The mails are encrypted end to end, so by default alerts and digests go out as they are, with XMPP account names and the servers' own addresses. SANITIZE=on replaces them exactly as vpsfort-tg-bot does for Telegram (the same code, src/redact.rs and src/servers.rs):

  • every XMPP address (alice@example.org, ejabberd:alice) becomes a pseudonym [acct:1a2b3c], an HMAC under PSEUDONYM_KEY (made on the first start, the bot's, 600); vpsfort-mail-bot pseudonym alice@example.org on the server tells which is which;
  • the servers' own addresses and host names in SERVER_NAMES become their node ids (nextcloud.example.org:443 → nextcloud.node1:443); attackers' addresses stay.

The weekly abuse report is never changed (as on Telegram). The Telegram bot sanitizes always.

The mail server

SMTP_TLSportlogin
the local Postfixnone (only allowed to 127.0.0.1, ::1, localhost)25usually SMTP_AUTH=none
a provider or another servertls (TLS from the start) or starttls (required: never falls back to plain)465 / 587SMTP_AUTH=auto (PLAIN or LOGIN, whichever is offered), plain, login

The server's certificate is checked against the system's CAs (/etc/ssl/certs) and SMTP_TLS_NAME (default: SMTP_HOST), or only against SMTP_CA_FILE (a server with a certificate of its own CA). A login is never sent over plain SMTP to another host: that setting is refused. The password goes in SMTP_PASSWORD_FILE (root:vpsfort-mail-bot 640).

What the server says decides what happens:

  • Out of reach, 4xx, TLS failing: the message waits; the bot tries again after 30 s, doubling up to 30 minutes. Alerts older than ALERT_MAX_HOURS (24) are dropped and counted in one mail; files after OUTBOX_MAX_DAYS (7).
  • 5xx for one mail (too large, rejected as spam): the bot sends a short note in its place saying what was refused and where to find it (vpsfort's actions log, or how to make the report again). If the note goes through, the refused mail is dropped.
  • 5xx for every mail (the sender or a recipient refused): the note fails too, the message waits, and the bot tries every 30 minutes.
  • A refused login (530, 534, 535, 538): no note is tried (it would be one more failed login towards the server's ban); the message waits, retried every 30 minutes. At the start it stops the bot with exit 78, which systemd doesn't restart.
  • No STARTTLS offered where SMTP_TLS=starttls: nothing is sent, not even the login, and the bot keeps retrying with backoff rather than giving up for good (someone in the way may be stripping it, and must not be able to stop the bot).

The bot opens one connection per mail (a few a day).

How vpsfort and the bot meet

The outbox (/opt/vpsfort-mail-bot/outbox, root:vpsfort-mail-bot 1770, sticky) has the format of the other bots: alert-*.msg with To: and Subject: lines, a blank line and the text, written under a dot name and renamed into place, owned by the bot's user. The bot claims one by renaming it to .<name>.sending, sends it, deletes it; if sending fails it renames it back (and on the next start it puts back what a stop left half-sent). The weekly report is any other regular file. vpsfort ([notify] mail_outbox, mail_user) puts a copy of every message for the first admin there (every admin message on a node with xmpp = false or no admins), and the abuse report job puts the report there. vpsfort warns the admins (over XMPP and to the Telegram bot, else as a system alert) when the bot leaves something unsent longer than bot_stuck_after.

Install from a release bundle

Instead of deploy.sh (below), without a Rust toolchain: every version tag vpsfort-mail-bot-v<version> gets its bundle, vpsfort-mail-bot-<version>-<commit>-<arch>.zip for each architecture (x86_64-linux-musl, aarch64-linux-musl for arm64, armv7-linux-musleabihf for 32-bit ARMv7 with hardware floating point), as an asset of the tag's GitHub Release (see "Releases" in the repository README); CI also keeps one for every commit as a workflow artifact (they expire and need a GitHub login), and scripts/bundle.sh builds it locally. It holds the static binary, the unit, config.env.example, SHA256SUMS and install.sh.

Download and verify (on your machine, then copy the zip over, or on the server): take the zip for the server's architecture (uname -m: x86_64, aarch64, or armv7l for armv7) from the GitHub Release of the version's tag, with the GitHub CLI or from the Releases page (each crate's releases are tagged vpsfort-mail-bot-v<version>):

arch=x86_64-linux-musl     # the server's: aarch64-linux-musl (arm64), armv7-linux-musleabihf (32-bit ARM)
gh release download vpsfort-mail-bot-v0.5.1 --repo makhort/vpsfort --pattern "*-$arch.zip*"   # the zip, its .sha256 and .sigstore.json
sha256sum -c vpsfort-mail-bot-*-$arch.zip.sha256              # the download is intact (macOS: shasum -a 256 -c)
gh attestation verify vpsfort-mail-bot-*-$arch.zip --repo makhort/vpsfort --source-ref refs/tags/vpsfort-mail-bot-v0.5.1

gh attestation verify (after gh auth login) checks the signed build provenance: that this repository's CI built exactly this zip from that tag. With --bundle vpsfort-mail-bot-*-$arch.zip.sigstore.json it checks the attestation attached to the Release instead of fetching it from GitHub. Only a public repository's releases have one (GitHub offers attestations for private repositories only with Enterprise Cloud).

On the server (apt install unzip or dnf install unzip if needed):

arch=x86_64-linux-musl     # as above: aarch64-linux-musl, armv7-linux-musleabihf on ARM
unzip vpsfort-mail-bot-*-$arch.zip && cd vpsfort-mail-bot-*-$arch
sudo ./install.sh          # install or upgrade; the first time also /opt/vpsfort-mail-bot/config.env
sudo ./install.sh rollback # back to the previous version

The first install, as with deploy.sh, doesn't start the bot until config.env is filled in (then run it again). install.sh checks every file against SHA256SUMS in a copy only root can write, then runs the same installer as deploy.sh (./install.sh --check only checks the files).

Install from a package

The same release has a package per architecture, for the distribution's package manager instead of install.sh: vpsfort-mail-bot_<version>-1_<arch>.deb (amd64, arm64, armhf; Debian, Ubuntu and their derivatives) vpsfort-mail-bot-<version>-1.<arch>.rpm (x86_64, aarch64, armv7hl; Fedora, RHEL and its rebuilds) and vpsfort-mail-bot-<version>-r0.<arch>.apk (x86_64, aarch64, armv7; Alpine, with OpenRC: below), each with its .sha256 and .sigstore.json, downloaded and verified as the bundle above (--pattern "*.deb*", "*.rpm*" or "*.apk*"). CI keeps them for every commit as workflow artifacts, and scripts/package.sh builds them locally (cargo install cargo-deb cargo-generate-rpm --locked once, and python3 for the .apk, which scripts/apk.py at the repository's root writes; none needs dpkg, rpm or apk-tools, so it runs on macOS too; --target aarch64-unknown-linux-musl or armv7-unknown-linux-musleabihf for the ARM ones). Or from the signed apt and dnf repository on GitHub Pages, once it is set up (the repository README, "Deployment"), where apt upgrade and dnf upgrade then bring new versions.

sudo apt install ./vpsfort-mail-bot_0.5.1-1_amd64.deb     # Fedora, RHEL:  sudo dnf install ./vpsfort-mail-bot-0.5.1-1.x86_64.rpm
sudoedit /opt/vpsfort-mail-bot/config.env                 # the first install put the template there
sudo systemctl enable --now vpsfort-mail-bot

The package puts the same files in the same places as install.sh (/opt/vpsfort-mail-bot with the binary and config.env.example, the user vpsfort-mail-bot, /var/log/vpsfort-mail-bot, the logrotate rule), except the unit, which is in /usr/lib/systemd/system. Its post-install step does what install.sh does apart from copying files: the user, config.env from the template the first time, the owners and modes, the outbox and the log directory; and it prints what is left to do ("Setup": the addresses, the mail server, the recipients' OpenPGP keys). dpkg-reconfigure vpsfort-mail-bot (rpm: dnf reinstall ./vpsfort-mail-bot-*.rpm) runs that step again, e.g. after copying a key there. apt remove vpsfort-mail-bot (dnf remove) stops the bot and keeps /opt/vpsfort-mail-bot; apt purge vpsfort-mail-bot removes it with the state and keys (rpm: by hand).

Nothing starts on its own. The first install puts the template in place and prints what to fill in; you enable the service once it is filled in. An upgrade keeps the config and restarts the service only if it was running and the config is filled in. Over a bundle or deploy.sh install the package takes over: the config, state and keys stay; the bundle's unit in /etc/systemd/system (it would shadow the package's) and its rollback files go, and the service is enabled again on the package's unit if it was (vpsfort's integrity watch reports the removed unit as a warning once). Replacing the config: when a terminal is there, the install asks whether to replace the config with the new template (the old one kept with the suffix .old); Enter, a timeout of a minute, no terminal or DEBIAN_FRONTEND=noninteractive keep it. VPSFORT_PACKAGE_CONFIG=replace (or keep) answers without asking: sudo VPSFORT_PACKAGE_CONFIG=replace apt install ./<file>.deb. Rollback is installing the previous version's package (apt install ./<old>.deb --allow-downgrades, dnf downgrade ./<old>.rpm): there is no .prev file.

Alpine (apk, OpenRC): apk add --allow-untrusted ./vpsfort-mail-bot-<version>-r0.x86_64.apk puts the same files in the same places, with the OpenRC script /etc/init.d/vpsfort-mail-bot instead of the unit: the settings exported from config.env as EnvironmentFile= does, supervised by supervise-daemon and started again 5 seconds after a crash; systemd's sandboxing has no equivalent there. The package is unsigned, hence --allow-untrusted: sha256sum -c and the attestation verify it. Its install scripts are POSIX sh and do what the post-install step above does: the user, config.env from the template the first time, the owners and modes, the log directory; an upgrade restarts a running bot. Then rc-update add vpsfort-mail-bot default && rc-service vpsfort-mail-bot start. apk del vpsfort-mail-bot stops it and keeps /opt/vpsfort-mail-bot. Not yet run on an Alpine host: CI installs the package in an Alpine container.

Setup

On your Mac:

./deploy/deploy.sh vpn

It runs scripts/ci.sh, builds the static binary, copies it with the unit and install.sh to the server and prints the command to paste into a root shell there. The first install creates the user vpsfort-mail-bot, /opt/vpsfort-mail-bot/config.env from config.env.example, and doesn't start the bot until it's filled in. Then, as root:

  1. Fill in config.env: MAIL_FROM, MAIL_TO, the mail server.
  2. Copy the recipients' public keys to /opt/vpsfort-mail-bot/recipients.asc (Thunderbird: Account settings → End-to-end encryption → OpenPGP Key Manager → File → Export; or gpg --armor --export you@example.org), and the SMTP password to smtp-password.
  3. Optionally, the signing key: set -a; . /opt/vpsfort-mail-bot/config.env; set +a; /opt/vpsfort-mail-bot/vpsfort-mail-bot keygen --out /opt/vpsfort-mail-bot/signing.key and SIGNING_KEY=/opt/vpsfort-mail-bot/signing.key in config.env.
  4. bash /opt/vpsfort-mail-bot/install.sh again (it sets owners and modes of the keys and files), then:
set -a; . /opt/vpsfort-mail-bot/config.env; set +a
/opt/vpsfort-mail-bot/vpsfort-mail-bot check        # connects, logs in, sends nothing
/opt/vpsfort-mail-bot/vpsfort-mail-bot send-test    # one test mail
systemctl enable --now vpsfort-mail-bot
  1. In [notify] of /etc/vpsfort/vpsfort.toml: mail_outbox = "/opt/vpsfort-mail-bot/outbox" and mail_user = "vpsfort-mail-bot", restart vpsfort, and vpsfort -c /etc/vpsfort/vpsfort.toml notify-test --mail.

For SPF/DKIM, MAIL_FROM should be an address the mail server may send as; otherwise the mails may land in spam. install.sh rollback goes back to the previous binary and unit.

Settings

Every option is also an environment variable (config.env is the unit's EnvironmentFile); vpsfort-mail-bot --help lists them with their defaults. deploy/config.env.example explains each one.

Retention and what the bot keeps

  • Outbox files until they are sent (alerts 24 h at most, files 7 days).
  • Its log, /var/log/vpsfort-mail-bot/bot.log (owner only): what was sent to whom, and the mail server's answers; rotated weekly, no line older than 14 days. No message text.
  • Nothing else: no state file. With SANITIZE=on, the pseudonym key. The service makes it on its first start; the one-off commands (check, send-test, pseudonym), run as root, never do, so it stays the bot's.

The unit is hardened like vpsfort-tg-bot's: no capabilities, a read-only system but its two directories, IPv4 and IPv6 sockets only, no writable-executable memory, and 128 MB of memory at most (MemoryMax).

Build and test

./scripts/ci.sh

Format, clippy, the tests, cargo audit, and the static x86_64-unknown-linux-musl binary (TARGET=aarch64-unknown-linux-musl ./scripts/ci.sh, or armv7-unknown-linux-musleabihf, for ARM). tests/fake_smtp.rs runs the bot against a fake mail server on 127.0.0.1 (plain, STARTTLS and TLS with a test CA, PLAIN and LOGIN, a server that strips STARTTLS, refusals) and runs the binary as systemd would; it needs to bind 127.0.0.1. tests/gpg_interop.rs needs gpg (skips without it). SMTP is lettre (blocking, rustls with ring: no OpenSSL), OpenPGP is rpgp, both pure Rust.

Fuzzing. What comes from outside (vpsfort's outbox files with attackers' log text in them, other files there, the recipients' key file, the signing key) goes through four cargo-fuzz targets (code in src/fuzzing.rs). Besides no panics, each checks the promises with rules of its own:

  • alert_mail: an outbox file to the finished mail, with SANITIZE off and on. The mail is all ASCII with CRLF line ends and lines under 998 characters; it has exactly the bot's own outer headers (subject ...) and, between the boundaries, only the version part and the armored message. Decrypted, it has the fixed protected headers, the subject on one line, and the text back unchanged; with SANITIZE=on, no account address and no server address or host name of the fuzzed setup is left.
  • file_mail: a file (name, NUL, content): text as the mail's text, anything else attached under a safe name, back byte for byte.
  • openpgp_keys: the key file; whatever is taken must encrypt to every usable address.
  • signing_key: whatever is taken signs mails that verify, in a well-formed Autocrypt header.

tests/fuzz_smoke.rs runs them on stable on realistic inputs, the seeds in fuzz/seeds/ and a few thousand mutations, so cargo test keeps them working; a failing input is saved as target/fuzz-smoke-<target>.bin (VPSFORT_MAIL_BOT_WRITE_SEEDS=1 cargo test --test fuzz_smoke regenerates the seeds; the keys in them, the signing key's secret part too, are throwaway). The real search needs nightly:

rustup toolchain install nightly --profile minimal && cargo install cargo-fuzz --locked   # once
cargo +nightly fuzz run alert_mail fuzz/corpus/alert_mail fuzz/seeds/alert_mail -- -dict=fuzz/alert_mail.dict -max_len=8192 -max_total_time=600

New inputs collect in fuzz/corpus/, crashes in fuzz/artifacts/ (both git-ignored). The regression-* seeds are inputs the first runs (2026-10-17) failed on, all fixed: a subject holding =?utf-8?b?…?= went into the header as it was, so mail clients would have shown it decoded, as other text (now encoded); a damaged signing key whose secret part no longer matched its public part was taken, and every mail would have carried a bad signature (now refused at the start); with SANITIZE=on, a server address replaced by its node id completed an address (admin@::ffff:192.0.2.10 → admin@node1; fixed in vpsfort-tg-bot too). One was the oracle's: a pseudonym cut by the 200-character subject limit.

Tested on a server (since 2026-10-20): a Debian VPS deployed with deploy.sh, the unit running. check, send-test, vpsfort's notify-test --mail (picked up from the outbox and sent within seconds), a digest (digest --send), real alerts (a source gone quiet, new listeners, a cluster node not responding) and the weekly abuse report, all through a provider (SMTP_TLS=tls, port 465, LOGIN) to a SimpleLogin alias forwarding to Proton Mail. Proton Mail on Android decrypts and shows them; GnuPG on a Mac decrypts the exported mails and shows the bot's signature as good. Proton re-armors the encrypted part and exports it quoted-printable with CRLF line ends, which turns every = in the armor (the base64 padding and the checksum line) into =3D and makes gpg report a CRC error or a malformed CRC. Undo that before decrypting a mail exported from Proton (only there: base64 itself never holds =3D, apart from a checksum that happens to start with 3D):

sed 's/=3D/=/g' mail.eml | gpg --decrypt
